# Архитектура Job Tracker

Этот документ описывает текущую систему как она работает в коде. Его цель — помочь
разработчику или ИИ безопасно менять агрегатор, не ломая историю вакансий, синхронизацию
и выгрузки.

## Назначение и границы системы

Job Tracker — локальный ETL-агрегатор вакансий. Он собирает открытые вакансии с публичных
карьерных сайтов и API компаний, приводит их к единому виду, сохраняет историю изменений
в SQLite и строит выгрузки для сайта, CSV и Telegram.

Это не система персональных рекомендаций. Пользовательские предпочтения, ранжирование и
подбор под конкретного человека должны находиться на сервере или во фронтенде, поверх
собранного набора вакансий.

## Карта компонентов

```text
config*.json
    │
    ▼
job_tracker.py: sync
    ├── HTTP-клиент httpx + лимит одновременных запросов на домен
    ├── адаптеры источников (HH, Greenhouse, Lever, HTML и специальные API)
    ├── нормализация → Job
    ├── обычные конфигурационные фильтры
    └── SQLite: jobs / events / runs
             │
             ├── data/jobs.csv
             ├── data/vacancies.js → frontend
             └── Telegram-уведомления
```

## Модель данных

### `Job`

Все адаптеры обязаны вернуть список неизменяемых объектов `Job`. Ключевые поля:

- `source_key` — постоянный ключ источника из конфигурации;
- `external_id` — постоянный идентификатор вакансии у источника;
- `company`, `title`, `location`, `team`, `workplace_type`, `description`, `url`;
- `posted_at`, `source_updated_at` — даты, если источник их предоставляет.

Пара `(source_key, external_id)` — идентичность вакансии. Менять `source_key` после
первой синхронизации нельзя: это создаст новые записи и потеряет связь с историей.

### SQLite

| Таблица | Роль |
| --- | --- |
| `jobs` | Текущее состояние вакансии и даты первого/последнего обнаружения. |
| `events` | История: `new`, `updated`, `closed`, `reopened`, `stale`, `restored`, `filtered`. |
| `runs` | Результат каждого запуска отдельного источника, включая ошибки. |
| `notifier_state` | Курсоры и состояние Telegram-уведомлений. |

Активная вакансия — `active=1 AND stale=0`. По умолчанию CSV, сайт и Telegram используют
только такие записи. Закрытые и устаревшие записи не удаляются: это позволяет восстановить
вакансию при следующем появлении и сохранить аудит изменений.

## Поток синхронизации

1. `load_config()` проверяет базовые поля и уникальность ключей источников.
2. `run_sync()` захватывает файловую блокировку базы. Повторный запуск завершается с кодом `3`.
3. `_run_sync()` создаёт общий `httpx.Client`, лимитер доменов и параллельно загружает источники.
4. `fetch_source_jobs()` выбирает функцию из `SOURCE_ADAPTERS`.
5. Адаптер возвращает унифицированные `Job`; для HTML применяются защитные проверки от
   навигационных ссылок и пустых результатов.
6. `matches_filters()` применяет только явные фильтры из конфигурации: ключевые слова,
   локации и стоп-слова.
7. Результат одного источника записывается в отдельной SQLite-транзакции через
   `persist_source()`. Ошибка записи откатывает только этот источник.
8. Для неавторитетных источников `mark_stale_jobs()` скрывает давно неподтверждённые вакансии,
   не закрывая их.
9. Экспорт строится отдельными командами, без повторного сетевого сбора.

## HTTP и параллелизм

- Используется общий `httpx.Client` на один запуск, чтобы повторно использовать соединения.
- `http.source_workers` задаёт параллелизм между источниками; обычное значение — `6`.
- `http.per_domain_workers` ограничивает одновременные запросы к одному домену; обычное
  значение — `2`.
- Запись в SQLite намеренно остаётся последовательной: это упрощает транзакционность и
  исключает гонки в истории вакансий.
- Повторы сетевых запросов имеют задержку с jitter и учитывают числовой `Retry-After`.

Не повышайте лимиты без необходимости: карьерные сайты могут ограничивать частые запросы.

## Статусы источников

`authoritative: true` означает, что адаптер гарантированно видит полный каталог вакансий.
Тогда отсутствующая позиция после `close_after_missing_runs` успешных запусков закрывается.

Для обычного HTML-скрейпера используйте `authoritative: false`, пока полнота пагинации и
фильтров не доказана. Такие вакансии не закрываются автоматически; они становятся `stale`
после `stale_after_days` без подтверждения.

## Как добавить или изменить источник

1. Выберите публичный структурированный API раньше HTML-скрейпинга.
2. Добавьте адаптер с сигнатурой `(source, timeout, retries) -> list[Job]` в `job_tracker.py`.
3. Зарегистрируйте его в `SOURCE_ADAPTERS`.
4. Добавьте запись в конфиг с постоянным `key`, `company`, `type` и параметрами адаптера.
5. Укажите честный `min_expected_jobs`, если адаптер умеет проверять подозрительно пустой ответ.
6. Для HTML используйте `job_url_pattern`, нормализуйте заголовок и проверяйте ссылки на
   вакансии, а не пункты меню.
7. Напишите тест с замоканным `fetch_json()` или `fetch_text()`; тест не должен обращаться
   к реальному сайту.
8. Запустите `python -m unittest discover -s tests -v`.

Не обходите CAPTCHA, авторизацию, robots-ограничения или антибот-защиту. Если у компании нет
публичного машиночитаемого списка, лучше оставить ссылку на карьерный сайт, чем делать хрупкий
или недопустимый парсер.

## Изменение фильтров

Фильтры — механизм качества общего каталога, а не рекомендаций. Используйте их только для
явно нежелательных позиций, например технического мусора HTML-страницы или нерелевантной
подборки конкретного источника. Не добавляйте глобальную классификацию «IT / не-IT» без
согласованной таксономии: агрегатор должен сохранять и digital-роли.

После изменения стоп-слов можно запустить:

```powershell
python job_tracker.py --db data/jobs.sqlite3 prune-excluded --config config.direct.json
```

Команда только помечает записи неактивными и записывает событие `filtered`; физически вакансии
из истории не удаляются.

## Проверки перед изменением

```powershell
python -m py_compile job_tracker.py tests/test_job_tracker.py
python -m unittest discover -s tests -v
```

Для изменения конфигурации дополнительно убедитесь, что JSON читается, и не запускайте полный
сбор только ради проверки формата: он обращается к внешним сайтам и обновляет рабочую базу.

## Направления дальнейшего развития

Первый безопасный срез уже выполнен: модели, фильтры, SQLite-хранилище, HTTP-транспорт и
экспорт находятся в пакете `jobtracker/`. Следующие срезы должны сохранять контракт `Job`
и SQLite-схему:

1. `transport.py` — HTTP-клиент, повторы и лимитер доменов.
2. `adapters/` — один модуль на семейство источников.
3. `storage.py` — схема SQLite, транзакции и события.
4. `exports.py` — CSV, сайт и Telegram.
5. `cli.py` — аргументы команд и orchestration.

Перед таким рефакторингом сначала расширьте тесты на поведение, затем переносите компоненты
маленькими независимыми изменениями.
